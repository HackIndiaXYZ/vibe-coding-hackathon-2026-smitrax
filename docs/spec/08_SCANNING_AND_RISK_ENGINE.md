# 08 - Scanning and Risk Engine

## Scanner goals

PatchPilot must answer:

1. Which projects are affected?
2. Which package/version is vulnerable?
3. Is a fixed version available?
4. How urgent is it?
5. Is the affected project deployed?
6. Can Codex safely patch it?
7. How confident is the fix?

## MVP ecosystem

Start with Node.js/npm.

Supported files:

- `package.json`
- `package-lock.json`

Optional phase 1.5:

- `pnpm-lock.yaml`
- `yarn.lock`

## Scanner adapter priority

### Preferred path: OSV-Scanner CLI

Run:

```bash
osv-scanner --format json --recursive <workspace>
```

or use current OSV-Scanner JSON flag syntax after checking installed version.

Why:

- Handles lockfiles more accurately.
- Uses OSV data.
- Reduces custom parsing.

### Fallback path: OSV API

Use OSV batch query for direct dependencies when lockfile scanning is unavailable.

Endpoint:

```text
POST https://api.osv.dev/v1/querybatch
```

Payload shape:

```json
{
  "queries": [
    {
      "version": "4.17.20",
      "package": {
        "name": "lodash",
        "ecosystem": "npm"
      }
    }
  ]
}
```

Important:

- Fallback has lower confidence without lockfile/transitive resolution.
- Mark findings with `scanConfidence: direct_manifest_only`.

## Enrichment sources

### EPSS

Endpoint:

```text
https://api.first.org/data/v1/epss?cve=CVE-2021-23337
```

Use fields:

- `epss`
- `percentile`

### CISA KEV

Use JSON feed from CISA or the GitHub mirror.

Fields to use when available:

- CVE ID.
- Vendor/project.
- Product.
- Vulnerability name.
- Date added.
- Due date.
- Known ransomware campaign use if present.

### NVD

Use NVD for details/CVSS enrichment when needed.

Endpoint stem:

```text
https://services.nvd.nist.gov/rest/json/cves/2.0
```

Do not block core scanning if NVD is slow/unavailable.

## Risk score formula

Risk score range: 0-100.

Recommended MVP formula:

```text
base = severity score
+ EPSS boost
+ KEV boost
+ production exposure boost
+ direct dependency boost
+ fix availability boost
+ package quarantine boost
- validation confidence penalty
```

### Severity score

If CVSS available:

- CVSS 9.0-10.0: 40
- CVSS 7.0-8.9: 30
- CVSS 4.0-6.9: 18
- CVSS 0.1-3.9: 8

If no CVSS:

- Critical label: 40
- High: 30
- Medium: 18
- Low: 8
- Unknown: 12

### EPSS boost

- EPSS percentile >= 0.95: +20
- >= 0.90: +15
- >= 0.75: +10
- >= 0.50: +5

### KEV boost

- In KEV: +25

### Exposure boost

- Production exposed: +15
- Deployment linked but not confirmed production: +8

### Dependency type boost

- Direct dependency: +10
- Transitive dependency: +4

### Fix availability boost

- Fix available: +5 because it is actionable.
- No fix available: +0 but mark manual review.

### Package quarantine boost

- Known malicious package report: +35
- Install script in new package: +12
- Version/package published very recently: +8
- Suspicious downgrade/substitution: +15

### Penalties

- Scan confidence low: -5 from confidence, not risk.
- Validation failed: fix confidence <= 40, not risk.
- Missing tests/build: fix confidence penalty.

Clamp final score to 0-100.

## Risk levels

- 0-29: Low
- 30-59: Medium
- 60-79: High
- 80-100: Critical

## Fix strategy selection

### safe_patch

Use when:

- Fixed version is patch version.
- No major upgrade required.
- Lockfile can update cleanly.

### minor_upgrade

Use when:

- Minor version upgrade fixes vulnerability.
- Breaking change risk moderate.

### major_upgrade

Use when:

- Only major version fixes vulnerability.
- Requires Codex to check breaking changes.
- Requires manual approval.

### mitigation

Use when:

- No safe version available.
- Config/code workaround exists.

### manual_review

Use when:

- No fix.
- Exploit critical.
- Dependency tree is complex.
- Codex cannot validate.

### no_fix

Use when:

- Advisory is not applicable after context analysis.
- Requires explicit audit note.

## Fix confidence score

Range: 0-100.

Inputs:

- Minimal version bump: +20
- Lockfile updated: +15
- Tests passed: +25
- Build passed: +20
- No unrelated files changed: +10
- No secrets touched: +5
- Small diff: +5

Penalties:

- Missing tests: -10
- Missing build: -10
- Major upgrade: -15
- Validation skipped by config: -20
- Codex changed unrelated files: -25
- New install scripts introduced: -20

## Demo fixture

Use a local test project with:

```json
{
  "name": "patchpilot-vulnerable-demo",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "test": "node test.js",
    "build": "node build.js"
  },
  "dependencies": {
    "lodash": "4.17.20"
  }
}
```

Known expected finding:

- Package: `lodash`
- Vulnerable version: `<4.17.21`
- Example CVE: `CVE-2021-23337`
- Fixed version: `4.17.21`

The test fixture must be generated by tests or committed under `tests/fixtures/vulnerable-npm-project`. If network is unavailable in CI, mock OSV response only in tests and label it as a fixture.
